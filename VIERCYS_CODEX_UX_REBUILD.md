## Booking rules and edge cases: implement BEFORE polishing
- Room inventory: exactly 20 distinct room IDs, mapped to 10/6/4 tiers. Operational state (active/maintenance) separate from reservation overlap.
- Validate check-in date >= property-local today; check-out strictly later; year constrained to realistic supported range (e.g., current year through current year+2), no `222222` year, no impossible dates, no negative durations, no NaN, no stale dates. Set calendar min/max AND server validation. Account for Santorini local timezone and daylight saving when computing calendar nights (date-only arithmetic).
- Voucher covers exactly min(3, eligible booked nights) ROOM NIGHTS of one eligible room in its designated tier or stated base-rate allowance. State policy clearly: default voucher covers up to three Essential Room nights, before upgrades and extras; extra nights cost the applicable per-night rate. If higher room tier chosen, charge a clearly disclosed per-night upgrade difference for every booked night (including complimentary nights), unless a more precise business rule is documented and tested. If a guest books fewer than 3 nights, unused nights are not cash or a future credit; explain this. No cash refunds for demo credits.
- Example: 3 nights Essential -> zero simulated room charge (excluding explicitly priced extras); 5 nights Essential -> pay 2 extra nights; 3 nights Signature -> 3 upgrade differences; 5 nights Signature -> 3 base nights covered + 2 full additional nights + 3 upgrade differences, mathematically equivalent to 5 Signature nights minus 3 Essential nights. Taxes/fees: either include in displayed rates or itemize clearly; never invent real tax authority charges.
- Show clear line items: nightly rate, nights, room upgrade, voucher discount, extras, simulated amount due, all in one consistent currency. Prices must derive from a single server-side pricing function, with client preview matching server recomputation. Do not use fake payment gateways, collect real credit cards, or claim real charges. CTA should say "Confirm demo reservation" or "Continue to simulated checkout".
- Guest capacity depends on selected room's actual maximum; support adults, children, infants if appropriate, and parties >4 by allocating multiple rooms or presenting a clear multi-room booking flow. Do not silently allow over-capacity or impose arbitrary max 4. If group size cannot be accommodated, explain options and prevent invalid checkout.
- Same-date same-room overlapping bookings forbidden, with database-enforced atomicity/locking/transactional availability checks, including simultaneous submissions. Half-open ranges [check_in,check_out), so checkout and next check-in on same date are allowed. Cancellation releases inventory; maintenance blocks nights.
- Date/room changes and extensions must recheck availability, recompute price, preserve voucher policy, prevent double redemption, and send an updated confirmation. If extra nights unavailable, offer valid alternatives; do not alter the booking silently.
- Handle sold-out dates, expired/invalid/redeemed voucher, invite link forwarded, double click, refresh/back button, interrupted checkout, invalid email, email delivery failure, booking cancellation, timezone boundary, same-day policy, keyboard/touch, and direct deep links. Provide clear recovery messages and safe idempotent server endpoints.
- Reservation lifecycle: pending/confirmed/cancelled/completed; do not mark paid or email-sent unless true. For demo payment, label status simulated. Do not require an account to reserve.
